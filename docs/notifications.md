# 站内通知

## 范围与入口

“消息 → 互动与系统通知”，或“设置与隐私 → 通知设置”。沿用 Pro 的导航、操作按钮、分段选择器、弹层和页面活动状态，不增加底部导航。

- 互动：点赞、评论／回复、好友申请通过。好友申请待处理入口保持原样，聊天未读数独立。
- 系统：动态／钓位／评论审核结果、社区举报处理结果、禁钓提醒审核更新。
- 仅产生部署之后的新事件；不补造旧通知。没有离线推送、系统通知权限申请或短信发送。
- 点赞、评论与回复可独立关闭。设置服务端保存，只影响之后事件；已有记录不删除。审核和举报处理结果不提供关闭开关。

## 权限与状态

迁移：`20261119211925_fishing_inbox_notifications.sql`，已部署至 `tlfmfokyhahlpzmpliad`。

通知和偏好放在 `fishing_private`，启用 RLS，客户端无表读写权限。对外仅 authenticated 可执行 `fishing_notifications`，内部入口核验 `auth.uid()` 和资料是否存在。生产者和内容投影函数不向客户端授权。

通知只存事件引用，不复制动态／评论正文、作者昵称、照片、坐标或审核员身份。列表读取、刷新和打开时按当前权限重新投影。删除、隐藏、转私密、拉黑或好友关系变化后，受影响的旧通知变成不可打开的中性提示，不占未读数；硬删除目标会级联删除相应通知。作者自己的审核结果可以打开仍然属于自己的未公开内容，但评论作者不能越过父动态权限。

打开评论通知进入所属动态，不承诺定位到某一条评论。举报结果进入本人“我的举报”，不是审核员详情；禁钓提醒结果进入“我的标记”。结果记录当时决定，详情以当前状态为准。

同一点赞取消再点赞不新增通知，也不重置已读；自己给自己点赞／评论不产生通知。业务提交、审核重试按事件键去重。回复同时命中动态作者和被回复作者时，每人只收一条。

## 分页与同步

- 每页 20 条，`bigint` ID 用十进制字符串传递；列表和游标使用同一 SQL 语句快照。
- 一次最多加载 200 条；未读显示最多 `99+`。不把通知数混入聊天数。
- “已显示的标为已读”仅提交实际加载的 ID，不影响刚收到而未显示的事件。
- 复用既有个人私有 Realtime 通道，仅发送 `{"v":1}` 失效信号；页面前台每 10 秒轮询兜底。列表原地核验权限，新事件提示手动刷新，不顶动阅读位置。
- 路由离开、应用后台、账号切换均失效旧请求并清除内存预览；恢复前台重新读取。不向本地存储写通知正文。网络／权限核验失败清除旧预览，并提供重试。
- 后台核验不禁用操作；用户主动保存可抢先处理，旧刷新响应不得覆盖新设置。主动保存期间显示进度，禁用态保留主题表面。空列表收到首条事件时不再同时显示“还没有通知”。

## 验证与限制

本地 PostgreSQL 数据库测试包含通知归属、内部函数不可调用、重复事件、自通知、偏好隔离、并发新事件不被批量已读、私密／拉黑／删除重投影、游标稳定性、禁钓提醒结果和级联清理。它不等同于 hosted 并发负载测试。

`node scripts/test-comments.mjs --notifications` 使用真实本地迁移和隔离 HTTP；`scripts/notifications-flow.mjs` 也用于临时真实 Auth 用户的 hosted 验收。实际截图检查三套皮肤的明暗、320／375／440px、横屏、宽屏、24／32px 根字号、键盘分段导航与弹层焦点。
