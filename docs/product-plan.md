# 钓友集首版产品规划

日期：2026 年 11 月 19 日。状态：已批准的产品基线；实际落地进度见 [实施状态](implementation-status.md)。

## 已确认的方向

应用名为钓友集。H5、微信小程序和 App 都纳入首版，账号和业务数据互通；采用用户新建的 Supabase 项目，架构参照 supabase-mobile-pro，设计应用 Apple Design 与 UI UX Pro Max 的原则。地图采用高德，参考 art-supabase-pro 的实现。

以下规则供实施和审阅使用，不代表全部已完成或上线。已确认：个人微信使用短信登录和高德地点搜索／静态预览，不使用微信手机号授权或内嵌 H5 地图；H5/App 保留完整地图。

## 产品主线

看到真实鱼情 → 找到合适钓位 → 出钓记录 → 选择分享 → 认识钓友 → 再次出钓。

钓友可能正在水边单手操作，也可能在家准备周末出钓。私人出钓日志和钓位收藏首先提供个人价值，之后把愿意分享的部分转为社区内容，让新社区也有持续使用的理由。

天气提供来源、区域和更新时间。气压、水温等缺失字段显示为未提供；首版以实际条件参考为主，渔获成功率需要另行验证。

## 导航与页面

四个固定入口为钓友圈、找钓位、消息、我的。记录属于动作，在首页和我的日志中可见，进入后选择晒渔获、写心得、记出钓、分享钓位。

| 区域 | 页面 |
| --- | --- |
| 账号 | 手机号登录、验证码、首次资料完善 |
| 钓友圈 | 信息流、搜索、话题、动态详情 |
| 发布 | 类型选择、图文编辑、渔获字段、范围设置、草稿 |
| 钓位 | 地图、列表、筛选、详情、选点、新增与编辑 |
| 出钓 | 日志列表、新建、详情、多条渔获记录 |
| 消息 | 会话列表、私聊、好友申请、互动通知 |
| 我的 | 个人主页、编辑资料、收藏、日志、关注与好友 |
| 设置 | 账号、隐私、黑名单、通知、帮助、注销 |
| 管理 | 举报队列、内容处置、账号限制与记录 |

游客先浏览公开内容；收藏、发布、互动和聊天时登录，完成后恢复原目标。首次资料完善可跳过。城市可手动选择；附近钓位使用明确授权的位置，同城钓友按城市和钓法推荐。

## 三端登录

| 平台 | 优先入口 | 备用入口 | 依赖 |
| --- | --- | --- | --- |
| H5 | 手机号加短信验证码 | 重发、更换手机号 | 短信服务、Supabase Phone Auth 和发送 Hook |
| 微信小程序（个人主体） | 手机号短信验证码 | 重发、更换手机号、游客浏览 | AppID、短信服务与 Supabase Phone Auth；不使用微信手机号授权 |
| Android 和 iOS | 运营商本机号码一键登录 | 手机号短信验证码 | 号码认证 SDK、包名签名、Capacitor 桥接 |

首次验证手机号即注册，后续同一已验证手机号进入同一账号。手机号以国家区号格式规范化；公开主页展示昵称、钓友号、城市与钓法。平台证明由服务端核验，登录成功需要取得可刷新、可撤销且能被数据库识别的 Supabase 会话。

覆盖手机号格式错误、验证码错误过期、重发冷却、请求受限、授权取消、号码认证不可用、重复点击、后台恢复、刷新失败与账号受限。协议由用户主动选择。验证码时效、错误次数和发送频率由服务端控制。

退出时清理私人缓存与会话订阅，保留公开浏览。换绑需要近期认证；遇到已有账号的号码进入明确的冲突处理流程。

## 内容与发布

心得和渔获属于动态；钓位独立保存，动态可以引用。私人出钓日志可以包含多条渔获，选择分享时生成独立动态草稿。

| 类型 | 最少输入 | 可选信息 |
| --- | --- | --- |
| 心得 | 正文或图片至少一项 | 标题、钓法、鱼种、饵料、话题、水域 |
| 渔获 | 照片或描述至少一项 | 鱼种、尾数、重量、长度、钓法、饵料、日志 |
| 出钓 | 日期、记录标题 | 起止时间、钓位、同行人备注、天气、多条渔获 |
| 钓位 | 名称、选点确认、水域类型、范围 | 鱼种、费用、停车、步行说明、照片、设施、信息时间 |

首版最多九张照片，正文建议最多两千字，校验与 API 统一配置。图片可排序、删除和预览，压缩并清理位置元数据后提供展示版本。kg、cm、尾为保存单位，输入可以换算斤。未称重保存为空，尾数零表示有效的空军记录。

发布流程：本机草稿 → 字段校验 → 媒体上传 → 服务端保存与权限校验 → 显示已发布或审核中。单张上传失败保留正文和其他结果，重复请求通过同一标识去重。

内容状态为 `draft → pending → published`；审核拒绝为 `rejected`，作者修正后重提；删除为 `deleted`，下架为 `hidden`。已发布内容修改时保存待审新版本，审核通过再替换公开版。作者看到审核与处理原因。

列表、详情、收藏、通知和分享链接遵循内容最新状态。打开不可见内容时提供说明和返回入口。

## 钓位隐私

| 独立维度 | 选项 | 决定什么 |
| --- | --- | --- |
| 内容范围 | 所有人、好友、仅自己 | 谁能看这条钓位与图文 |
| 地点精度 | 精确点、仅大致水域、不显示地点 | 获准阅读者能得到哪种位置 |

新建动态和钓位默认公开，保存前可调整谁可以看。已有草稿和记录保留原分享范围。钓位名称与真实选点地址独立保存；精确地址随钓位精度与范围展示。公开动态引用私人钓位时，保存作者选择的安全描述。

精确坐标独立授权读取。列表、地图标记、聚合、排序、距离、详细地址、路线终点和导航共同遵守精度规则。大致水域采用稳定区域或固定网格，重复请求返回同一公开区域。照片清理 EXIF；海报、消息卡片、链接预览均使用获准字段。

权限收紧后重新鉴权，签名访问采用短时策略。接收方已保存的截图或下载内容不能追回，分享范围说明需要表达这一实际限制。

## 水域地图流程

水域地图只呈现禁钓区域，不展示用户保存的钓位图钉、数量或列表。搜索和定位用于移动视图，点击禁钓边界查看说明、来源与反馈；标记入口进入边界圈选。初始定位只确定视图中心，选点用于保存钓位时仍须用户确认；迟到的定位和搜索不覆盖已选位置。

地点详情优先给出水域类型、鱼种、最近鱼情、费用来源与时间、到达说明。停车入口与岸边钓点分别记录，驾车优先到可到达入口，末段步行补充说明。支持失效、纠错与重复报告。

地图确定使用高德。个人微信使用原生页面的高德地点搜索与静态预览，不使用 `web-view` 或微信原生地图替代高德；H5/App 保留完整高德地图。

## 关注 好友与拉黑

关注是单向订阅，好友是双方同意的关系。互相关注仍单独处理好友申请。首版好友才能开始或继续私聊，陌生人通过申请留言表达来意。

申请状态为 `pending → accepted / rejected / cancelled / expired`。接收人接受或拒绝，发起人撤回。服务端合并交叉申请，相同用户对只有一个有效关系；重复申请有冷却。

删除好友后停止新消息，各自保留历史，重新加好友恢复原会话。拉黑阻止新申请、消息、关注和好友范围内容访问，终止好友关系，并在操作者列表屏蔽对方；解除后重新建立关系。对方显示中性的不可用状态。

按手机号找人默认关闭，使用昵称、钓友号、城市和钓法发现钓友。后续如提供手机号搜索，需由被搜索者主动开启并限制枚举。

## 聊天与通知

支持文本、图片、动态与钓位卡片。卡片携带引用和安全摘要，打开时校验当前权限。

草稿按用户和会话保存。点发送立即显示发送中，数据库确认后为已发送，对方实际阅读后为已读。超时先用消息标识核对是否已保存，再重试，保持同一条消息。首版实现发送与已读，网络连接本身不代表阅读。

历史按服务端游标翻页，断线恢复补齐数据。看历史时保持位置，收到消息显示有新消息入口。图片预留尺寸，键盘打开时输入与最新消息可见。

通知分互动、申请和系统，聊天未读独立计算。各端先提供站内通知；App 后台推送、小程序订阅消息与 H5 Web Push 分别配置和验证。

## 冷启动与内容管理

推荐初期用发布时间、有效互动和人工精选组合，统一遵守范围、拉黑和审核结果。搜索分动态、钓位、钓友；新用户选择城市、鱼种和钓法均可稍后修改。

没有关注内容时给同城公开内容和找钓友入口；没有钓位时可扩大区域或添加私人钓位。演示内容明确标注，生产社区使用真实记录和有来源的运营内容。

最小管理入口支持举报队列、隐藏与恢复内容、账号限制和处置记录；普通用户可屏蔽、拉黑。服务端校验发布权限、频率与内容，作者可查看原因并修正重提。

注销需近期验证、影响说明、确认和处理进度。私有资料、日志、媒体和关系按方案清理，会话内容采用统一匿名或删除规则，实施前固定保留范围。

## 首版验收清单

1. 同一手机号从三端登录，返回同一账号和资料。
2. 游客点收藏，登录后恢复原内容并完成操作。
3. 弱网单图上传失败后恢复，正文不丢且只有一条动态。
4. 私人日志生成公开草稿时，坐标与同行人备注保持受限。
5. 模糊钓位的地图、距离、导航与分享均无法取得精确点。
6. 非好友无法发消息，成为好友后可通信，删除或拉黑立即停止新发送。
7. 发送超时但已落库时，重试只有一条消息。
8. 后台恢复和重连补齐消息，未读计数一致。
9. 拒绝定位或地图失败仍可用城市搜索和列表。
10. 范围变化、删除和下架后的原链接按最新权限显示。
11. 320px、大字号、夜间与键盘下的页面和弹层可用。
12. API、Storage 和实时通道无法读取他人的私人日志及无权消息。

观察首条记录完成率、发布成功率、收藏回访、申请接受率、消息成功率和七日回访，并结合投诉、失效钓位和错误率决定迭代重点。
